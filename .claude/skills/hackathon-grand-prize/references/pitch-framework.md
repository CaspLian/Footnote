# Pitch Framework

Use for Phases 15–16. Build an evidence-backed spoken narrative around one problem, one innovation, one proof, and one impact—not a product tour.

## Inputs

Before writing, gather:
- official duration, format, and judging criteria with dated citations;
- one-sentence thesis and core differentiator;
- demo primary/fallback timing;
- architecture and sponsor proof;
- scorecard gaps and prohibited/unsupported claims;
- audience knowledge and call to action.

If the time limit is unverified, label timing provisional.

## Default 180-second allocation

| Time | Purpose | Required content | Visual |
|---:|---|---|---|
| 0–10s | Problem | Specific user, costly moment, credible evidence | Human/context, not logo animation |
| 10–25s | Gap | Why current workflow fails | Concise before state |
| 25–45s | Solution | Thesis and distinct mechanism | Product/core flow |
| 45–90s | Proof | Live magic moment and verified outcome | Demo, not slides |
| 90–120s | Technical credibility | Only architecture needed to explain why it works | Simple system trace |
| 120–150s | Sponsor + differentiation | Indispensable sponsor contribution and competitive edge | Observable contribution |
| 150–180s | Impact + close | Honest evidence, future leverage, memorable final line | Result and identity |

Scale segments proportionally for official limits, but protect live proof. Do not accelerate beyond intelligibility; cut content.

## Claim ledger

| Spoken claim | Verification FACT / ASSUMPTION / UNVERIFIED | Proof strength | Medium LIVE / SEEDED REPLAY / RECORDED / DOCUMENTED | Evidence/source/date | Visual proof | Risk if challenged | Safer wording |
|---|---|---|---|---|---|---|---|
| | | | | | | | |

Remove claims that cannot be defended in one sentence. Do not say “first,” “only,” “production-ready,” “secure,” “scalable,” or quantified impact without appropriate evidence.

## Narrative tests

- **Clarity:** a listener can repeat user, problem, solution, and difference.
- **Causality:** architecture and sponsor tech explain the result shown.
- **Proof:** the strongest claim is demonstrated, not deferred to roadmap.
- **Compression:** every sentence earns a criterion, transition, or understanding.
- **Integrity:** uncertainty and fixtures are labeled without undermining confidence.
- **Memory:** final line recalls the magic moment, not a feature list.

## Technical explanation pattern

Use: “When **[input]**, our **[specific component/sponsor capability]** performs **[mechanism]**, verifies **[criterion]**, and returns **[observable outcome]**. If **[failure]**, we **[fallback]**.”

Prefer one architecture trace over listing frameworks. Name sponsor technology naturally where its contribution occurs.

## Demo transition and fallback wording

Primary transition:
> “Here is the exact moment that changes the workflow: [action]. Watch [observable result].”

Fallback transition:
> “The live dependency is not responding within our safe limit, so I’m switching to our labeled deterministic replay of the same request and verification path.”

Recovery must preserve the narrative and avoid apologies or pretending cached output is live.

## Rehearsal

Record run date, speaker, actual duration, overrun point, unclear sentence, demo latency, fallback duration, and action. Rehearse interruptions and the top judge objections. Verify names, numbers, URLs, and sponsor terminology against official/current sources before final recording.

The pitch passes when it fits the official limit with buffer, the demo fallback also fits, every material claim has evidence or an honest label, speaker/visual cues are unambiguous, and the close states why this project should win.
