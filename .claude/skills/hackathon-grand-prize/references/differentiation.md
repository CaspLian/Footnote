# Differentiation Engine

Use for Phases 3–4. Differentiation must change user outcome or the visible workflow, not merely branding or model choice.

## Generate moves

Produce at least three moves from different mechanisms:

| Mechanism | Prompt | Proof in demo |
|---|---|---|
| Novel workflow | What painful handoff or sequence disappears? | Fewer steps, new interaction, before/after |
| Autonomy | What bounded goal can the system complete and verify? | Observable plan/actions/verification |
| Unique architecture | What capability becomes possible because of the design? | Trace, latency, resilience, local/privacy behavior |
| Sponsor centrality | What core outcome degrades if sponsor tech is removed? | Side-by-side contribution or trace |
| Human + AI | Where does human judgment improve or safely constrain automation? | Approval/correction loop |
| Unique UX | How is complexity made instantly legible? | Interaction judges can understand silently |
| Deployment realism | What real constraint is solved, not hand-waved? | Permission, offline, audit, edge, rollback behavior |
| Data/network effect | What legitimate reusable signal improves outcomes? | Proven feedback/state loop; no speculative moat |
| Measurable impact | What changes and how is it measured? | Labeled measured/simulated result |

## Falsification tests

A proposed differentiator fails if any answer is no:

1. **Removal:** Would removing it materially worsen the user outcome?
2. **Visibility:** Can a judge see or understand it within the demo window?
3. **Specificity:** Is it more precise than “AI-powered,” “real-time,” or “easy to use”?
4. **Mechanism:** Can the team explain how it works and show technical evidence?
5. **Alternative:** Is it meaningfully better than a manual process or common product?
6. **Feasibility:** Can the proof be built, rehearsed, and recovered within time?
7. **Integrity:** Is the impact claim correctly labeled and not fabricated?

## Product thesis

Fill without jargon:

> We built **[product]** for **[specific user]** that **[achieves observable outcome]**, unlike **[current alternative]** because **[core mechanism]**.

The magic moment is one visible state change: input becomes an outcome, the system takes a meaningful verified action, or a user catches/controls something existing tools miss. It is not login, configuration, a chat response alone, or an architecture slide.

## Cross-domain examples

These are patterns, not ready-made ideas:
- **AI:** agent proposes, uses bounded tools, verifies output, and routes uncertainty for approval—not a single completion call.
- **Hardware:** sensor signal triggers a safe local action and remains demonstrable with recorded input—not a dashboard of readings.
- **Web3:** verifiable ownership or coordination removes a trust bottleneck—not a token attached to CRUD.
- **Social impact:** constrained offline workflow proves access/privacy value with synthetic data—not unsupported population-scale impact.

Exit only when the core differentiator, thesis, architecture, and demo all describe the same mechanism.
